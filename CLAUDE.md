# CLAUDE.md — IDE Web (TCC)

## Stack
Backend: Node.js + Express + TypeScript (`ide-web-backend/`) | Frontend: React + TypeScript + Vite (`ide-web-front/`) | Banco principal: PostgreSQL via Supabase | API sob prefixo `/api/v1`.

## Hospedagem
Frontend: Vercel | Backend Node (app principal): Render | Banco principal (app): Supabase | Banco do sandbox SQL: projeto Supabase **separado** do banco principal (ver módulo sandbox SQL) | Backend de pesquisa (Python/FastAPI — pesquisa/TCLE/grupo/sessão/SUS/RTLX; a análise estatística fica **fora** do sistema, sobre o CSV exportado): **único serviço em Docker**, no servidor do autor, self-hosted, junto com o Postgres próprio dele (separado do Supabase) — `pesquisa-backend/docker-compose.prod.yml`, exposto por HTTPS via reverse proxy; front fala **direto** com ele (não passa pelo Node) — ver `docs/decisions/fase4-pesquisa-python-sessao-aluno-login.md` e `fase6-alinhamento-tcc.md`. **`pesquisa-backend/` não mora neste repositório** (open source): é exclusivo do período de coleta de dados do TCC e fica mantido à parte, fora do controle de versão público — ver "Restrições não-negociáveis". Dev local do resto da aplicação continua via `docker-compose.yml` da raiz (Postgres local + backend + frontend/nginx); pra rodar a pesquisa localmente, suba o compose próprio dela à parte e aponte `VITE_RESEARCH_API_URL` pro endereço resultante.

## Restrições não-negociáveis
- **Self-hosted obrigatório para dados de pesquisa com seres humanos** (TCLE/consentimento, grupo sorteado, respostas SUS/RTLX). Esse dado específico não pode ir para serviço cloud de terceiros — fica no backend Python/Docker do autor (self-hosted), nunca no Supabase. Já os dados "de produto" (Usuario, Turma, Exercicio, submissões, diagramas etc.) vão para o Supabase normalmente — a restrição é só sobre o dado de sujeito de pesquisa em si, não sobre a aplicação inteira. Se uma decisão futura tocar TCLE/SUS/RTLX e cogitar Supabase/BaaS gerenciado pra esses dados especificamente, isso viola esta restrição — pare e confirme.
- Chamadas a LLM (`LLM_API_KEY`, a partir da Fase 3) podem sair para um provedor externo, mas o **prompt/estado enviado** não deve incluir dados de identificação do participante além do necessário para a dica pedagógica.
- **O grupo controle/experimental (sorteado no backend Python depois do TCLE), o fluxo de pesquisa (`features/pesquisa`, `features/tcle`, `/admin/pesquisa`, `pesquisa.routes.ts` do Node) e a coleta SUS/RTLX são exclusivos do período de pesquisa do TCC.** O autor vai remover esse código manualmente depois da coleta de dados, antes do projeto (open source) servir como a ferramenta real de uso do IFPI. Ao tocar nessas partes, deixe a remoção fácil (não espalhe a lógica de sorteio/pesquisa por múltiplas camadas sem necessidade).

## Arquitetura — Backend
Camadas MSC: `routes → controllers → services → repositories`, conforme `backend-dev-guidelines`. Estrutura em `src/`: `config/`, `controllers/`, `services/`, `repositories/`, `models/`, `dtos/` (validação Zod), `errors/` (classes customizadas: `AppError`, `NotFoundError`, `ValidationError`, `UnauthorizedError`, `ConflictError`), `middlewares/` (`errorHandler`, `notFoundHandler`, `requireAuth`), `routes/`, `utils/`, `app.ts` + `server.ts`. Persistência via Prisma com driver adapter `@prisma/adapter-pg` (client singleton em `src/lib/prisma.ts`). Auth: cookie `httpOnly` `access_token`, JWT com um único `JWT_SECRET` (access 15min / refresh 7d), hash de senha via `bcryptjs`. **Desde a Fase 10 a sessão tem estado no servidor** (`SessaoAuth`): o token carrega `sid`, o `requireAuth` valida a sessão (revogada / 6h de teto / 1h de ociosidade, gravando atividade a cada 5min) e o logout revoga de fato — reverte o logout stateless da Fase 1. O `httpClient` do front renova no 401 e refaz a requisição. **Todo papel tem conta própria (e-mail + senha), inclusive o aluno** — a sessão leve por turma foi removida na Fase 8. **`POST /auth/registrar` só aceita `aluno`/`professor`** (Fase 12): `pesquisador` é conta única do autor, sem autocadastro, criada/atualizada por `ide-web-backend/scripts/seed-pesquisador.ts` (idempotente por e-mail, senha vem de variável de ambiente na hora de rodar, nunca fica no repositório). O código da turma virou matrícula, não credencial: `POST /turmas/:codigo/matricular` exige estar logado, e o aluno permanece na turma até o professor `POST /turmas/:id/encerrar` (reversível por `/reabrir`). `GET /pesquisa/token` emite um JWT curto (`RESEARCH_JWT_SECRET`, claims só `usuario_id`/`papel`/`turma_ids` — sem nome e sem e-mail) que o front usa como Bearer nas chamadas diretas ao backend Python de pesquisa. `GET /pesquisa/acertos?exercicioIds=` (só `pesquisador`) devolve tentativas/acerto/dicas por aluno nos exercícios da tarefa, pro CSV. Dica de IA recebe `{ contexto, estadoMer?, estadoSql? }` (estadoMer = documento de modelagem) e manda o resumo do conceitual (`utils/modelagem/resumoConceitual.ts`: entidades/atributos, `(mín,máx)` por participação, especializações) + o modelo lógico como SQL gerado (`utils/modelagem/gerarSql.ts`, espelho do front) + a query, pedindo coerência entre eles; sem lógico desenhado, o DDL vazio não vai. `POST /exercicios/:id/pacote` monta o PDF com até duas imagens dos modelos (rótulo + PNG vindos do navegador) e o SQL do modelo lógico; `GET /exercicios/:exercicioId/alunos/:usuarioId/diagrama` dá ao professor da turma leitura do modelo entregue pelo aluno. `POST /exercicios/:id/liberar-gabarito` tem par (`/ocultar-gabarito`): liberar por engano é reversível. **Acesso do aluno ao exercício passa por um ponto único, `AcessoExercicioService`** (`exigirLeitura`/`exigirEntrega`): exercício `publico` libera qualquer aluno logado, senão exige matrícula; turma encerrada congela em leitura (não aceita entrega), e exercício público não congela junto com a turma de origem. `POST /exercicios/:id/pacote` deixou de resetar o sandbox — baixar o PDF é repetível e sem efeito colateral, e quem encerra é `POST /exercicios/:id/finalizar` (grava `ResultadoExercicio.finalizado_em` e derruba o schema). Estudo livre: `GET /exercicios/publicos`, `POST /sandbox/livre/executar` e `DELETE /sandbox/livre` operam num schema `sandbox_livre_<usuario_id>` onde o aluno — e só ali — tem `CREATE`, para montar o próprio esquema. Erros do domínio falam português (`NotFoundError` monta "X não encontrado(a)"), porque a mensagem chega ao usuário; IA sem chave no ambiente responde `LLM_NAO_CONFIGURADO`, separado do 503 passageiro do provedor. `POST /sandbox/enviar` devolve o `plano` (EXPLAIN) e **grava o acerto em `ResultadoExercicio.sql_correto`** quando o exercício tem gabarito — sem sobrescrever revisão manual (`revisado = true` congela o valor): até a Fase 9 o acerto morria em `SubmissaoSql.correta` e nunca chegava ao resultado. Sem gabarito, `correta` continua nula e o aluno lê "será corrigido pelo professor" em vez de silêncio. `PATCH /exercicios/:exercicioId/alunos/:usuarioId/resultado` exige que o aluno tenha matrícula na turma do exercício, e `GET /exercicios/:exercicioId/alunos/:usuarioId/respostas` entrega ao professor a última submissão SQL e a dissertativa (a modelagem já tem rota própria). Modo prova (Fase 10): `AcessoExercicioService.exigirEntrega` pergunta, nesta ordem, turma encerrada → prazo (`Exercicio.prazo`) → envio único (`prova_id` não nulo + submissão existente); `exigirTeste` recusa testar em questão de prova. `ResultadoExercicio.envio_liberado_em` é a válvula: concede UM envio, atravessa prazo e envio único, e é consumida no `enviar`. Bloqueio de cópia no front é **dissuasão, não controle**. Assistente de prova: `GET /turmas/:turmaId/provas/acervo` e `POST /turmas/:turmaId/provas/assistente` distribuem exercícios sem prova (um exercício pertence a uma prova só). Notas vão de **0,0 a 10,0**. Painel: `GET /painel/professor`, `GET /painel/aluno`, `GET /turmas/:id/painel` e `GET /turmas/:turmaId/alunos/:usuarioId/atividades` (camada `painel`, agregação em `groupBy` e cruzamento em memória — ver `utils/painel.ts`, que concentra `exercicioVisivelParaAluno`, `temCorrecaoManual`/`aguardaRevisao` e `estadoDaCelula`, usados pelos dois painéis). Documento de modelagem v2 (`conteudo_json`, `mer_gabarito`) é validado por `dtos/modelagem.schema.ts` (espelho do front); `Exercicio.modo_mer` guarda o nível da modelagem — ver `docs/decisions/fase7-modelagem-conceitual-logica.md`.

## Arquitetura — Backend de pesquisa (Python, self-hosted)
FastAPI + Postgres próprio (Docker do autor, fora do Supabase) — ver `docs/decisions/fase4-pesquisa-python-sessao-aluno-login.md`. Guarda só o dado de sujeito humano: `Pesquisa` (turma, `exercicio_ids` da tarefa, sorteio, encerramento — no máximo uma ativa por turma), `TcleConsentimento` (por pesquisa, sem IP), `AlocacaoGrupo`, `SessaoUso` (uma por aluno por pesquisa, `ambiente` definido pelo servidor a partir do grupo), `RespostaSus`, `RespostaRtlx` (validam as escalas). `usuario_id`/`turma_id` são o mesmo UUID do Supabase, sem FK cruzando banco. Autenticação: valida o JWT curto emitido por `GET /pesquisa/token` no Node (`RESEARCH_JWT_SECRET` compartilhado só entre Render e o Docker do autor) — não tem login próprio, não chama o Node de volta. O claim é `turma_ids` (lista, Fase 8: o aluno pode estar em várias turmas) e `consultas.pesquisa_ativa_do_aluno` resolve qual delas tem pesquisa aberta — só este serviço conhece as pesquisas ativas. Só `papel: aluno` grava TCLE/sessão/SUS/RTLX, e o servidor exige TCLE aceito + grupo sorteado antes da sessão e sessão finalizada antes de SUS/RTLX. Só `papel: pesquisador` inicia/sorteia/encerra/lê participantes e exportação. Sorteio: `secrets.SystemRandom`, só entre quem aceitou o TCLE, metade/metade, idempotente (tardios vão pro grupo menor, ninguém é reatribuído). Sincronização entre as máquinas da turma é por polling (`GET /pesquisa/minha-participacao` pro aluno, `GET /pesquisa/status/:turma_id`), não WebSocket.

## Arquitetura — Frontend
Feature-based, conforme `frontend-dev-guidelines`. Estrutura em `src/`: `app/` (App.tsx, providers, `routes.tsx`), `features/<domínio>/` (cada uma com `components/`, `hooks/`, `services/`, `types.ts`, `index.ts`), `shared/components/` (`Button`, `Input`, `Modal`, `AuthGuard`, `PageStub`), `shared/hooks/`, `lib/` (`httpClient.ts`, com `credentials: 'include'`), `styles/`, `types/`. Editor de exercícios usa Monaco (`@monaco-editor/react`) + diagrama MER via `@xyflow/react` lado a lado em `/exercicios/:id`. Modelagem (Fase 7, `features/exercicio/modelagem/`): documento v2 (`documento.ts` — conceitual Chen + lógico + dados da conversão, validado igual ao Node), operações puras por modelo (`logico/operacoes.ts`, `conceitual/operacoes.ts`), conversão conceitual → lógico (`conceitual/conversao.ts`: `converter`/`identificarPendencias`/`assinaturaConceitual` — tabela por entidade reusando o id do elemento, FK no lado N, tabela própria pra N:N/n-ário e pra entidade associativa, atributo composto achatado em `pai_filho`, multivalorado em tabela `<dono>_<atributo>`, 1:1 e especialização perguntados ao aluno; passagens em ordem: entidades → especializações → associativas → fusões → demais relacionamentos → multivalorados; nunca lança erro, o que não converte vira aviso), `gerarSql.ts` (espelho do Node), histórico desfazer/refazer (`historico.ts`, `useDocumentoEditavel` — `aplicarLogico`/`aplicarConceitual`/`aplicarConversao`), autosave com retry/validação (`useAutosaveModelagem`), `sincronizacao.ts` (destaque bidirecional modelo↔consulta pelo SQL do lógico). Componentes em `components/modelagem/`: `EditorModelagem` escolhe o editor pelo nível do exercício (`modos.ts`: `modoDoExercicio`, que cai em `conceitual_logico` se vier valor desconhecido do banco) e registra em `capturaRef` a função que tira as imagens dos modelos pro PDF (no conceitual → lógico ela força cada aba por vez, espera o React Flow remontar e captura as duas), `ConceitualLogicoEditor` (abas Conceitual/Lógico — a segunda só abre depois de converter ou se já houver tabelas —, botão "Converter", `AssistenteConversao` com as perguntas 1:1 e prévia do resultado, aviso quando a assinatura do conceitual muda depois da conversão; os dois modelos ficam independentes depois disso, D7), `logico/LogicoEditor` (barra, paleta, painel de propriedades sobreposto, nós derivados do documento com `measured` guardado à parte), `conceitual/ConceitualEditor` (mesma casca; nó entidade/relacionamento — losango em SVG com `stroke`, nunca `clip-path` num elemento com borda, que só recorta a caixa original e não desenha contorno novo —, nó atributo em círculo (contorno duplo = multivalorado, filhos = composto) com alças invisíveis só pra `LinhaEdge` ter pontas, triângulo da especialização `(t|p, d|s)` ligado à genérica e às filhas, losango dentro de retângulo = entidade associativa, `(mín,máx)` por participação com curvatura crescente pra separar auto-relacionamento, `visaoAtributos` círculos/lista alternável na barra), usados pelo aluno (`ModelagemCanvas`), pelo professor ao montar o gabarito (`GabaritoModelagemModal`) e na revisão (`RevisaoModelagem`: abas modelo do aluno / gabarito, só leitura, dentro de `RevisaoAlunoPage`); `estilos.ts` concentra a identidade visual dos dois editores (caixa, contorno, alça — invisível em leitura —, traço das linhas e das formas SVG); `SqlModeloPainel` mostra o SQL do modelo (oculto no modo puramente conceitual, que não tem lógico). O Monaco fica dentro de `.nokey` (senão o React Flow engole a tecla Espaço no Chrome). Teste de navegador: `npm run e2e` (Playwright + Chrome do sistema, API simulada, `tests/e2e/*.e2e.ts`). `AuthGuard` cobre autenticação + papel (`professor`/`pesquisador` em `/admin/*`, `aluno` em `/tcle`, `/pesquisa/*` e `/estudar`); rota coringa `*` cai em `NaoEncontrado` (sem ela, URL desconhecida dava tela em branco) e o `DashboardPage` leva cada papel à área dele por cartões de atalho — o do aluno é "Estudar sozinho". A revisão é **por aluno** (`/admin/turmas/:turmaId/alunos/:usuarioId`, `RevisaoAluno`): uma tela com todas as atividades dele, notas 0–10, aviso de envio queimado por erro de sintaxe e botão "Liberar novo envio"; salvar volta à lista. `features/painel/` alimenta o `/dashboard`, que virou só um roteador por papel: `PainelProfessor` (cartões de resumo, `FilaCorrecao` do que exige humano, `CartaoTurma` por turma) com a matriz aluno × exercício em `/admin/turmas/:turmaId/painel` (`MatrizTurma` — `<table>` semântica, rótulo textual além da cor, célula ausente = exercício de outra prova — mais `ExerciciosDificeis`); e `PainelAluno` (banner de pesquisa **como primeiro elemento**, resumo, "o que falta fazer" atravessando as turmas, turmas agrupadas por disciplina, histórico, progresso **do aluno contra ele mesmo** — sem média, posição ou nome de colega). `features/estudo-livre/` (`/estudar`) é a IDE sem turma: abas "Meu banco" (SQL no schema livre, com "Limpar meu banco"), "Modelagem" (rascunho só do navegador, com "Usar no meu banco" levando o DDL gerado pro banco livre) e "Exercícios públicos". `FinalizarPacoteButton` tem dois botões separados — "Baixar PDF" (repetível) e "Finalizar" (confirma antes, avisando quando o aluno ainda não baixou o arquivo). Relatório de testes exploratórios e o que virou correção: `docs/erros-da-ferramenta/`.

Importar de outra feature **sempre pelo `index.ts`** dela, exceto quando o consumidor só precisa de um `service`/hook leve e a feature também exporta uma página pesada (ex.: `ExercicioPage` carrega Monaco) — nesse caso importar o arquivo concreto direto (`~features/exercicio/services/exercicioService`), pra não puxar a página pesada de graça. Já mordeu (Monaco quebrando em teste jsdom por causa de um import não usado de fato).

`features/pesquisa/` fala com o backend Python via `researchHttpClient.ts` (busca o token em `GET /pesquisa/token` no Node, cacheia até expirar, manda como Bearer) — nunca usa o `httpClient.ts` do Node pra essas chamadas (exceção: `acertosService`, que é endpoint do Node). Fluxo do aluno, **dirigido pelo servidor** via `useMinhaParticipacao` (polling 5s; nada em `sessionStorage`): banner em `AlunoTurmaPainel` → `/tcle` → `/pesquisa/sessao` (aguarda sorteio → "Iniciar tarefa" → exercícios da tarefa com cronômetro de referência de 60 min: experimental abre a IDE; controle usa `ControleEntrega` — copia o `sqlSetup`, entrega a query final uma vez, sem ver se acertou → "Finalizar tarefa") → `/pesquisa/sus` → `/pesquisa/rtlx`. `useBloqueioPesquisa` troca a `ExercicioPage` por um aviso pro grupo controle enquanto a pesquisa está ativa (bloqueio só no front). Pontuação SUS/RTLX é calculada **no frontend** e o Python valida as escalas. SUS = "Escala de Usabilidade de Sistema — versão brasileira" (Lourenço; Carmona; Lopes, 2022), RTLX = 21 marcas de 0 a 100 sem valor pré-marcado; os textos são os mesmos do Apêndice B do TCC. TCLE (`TermoTexto.tsx`, versão 2.0 = Apêndice A) tem só o contato do CEP pendente — preencher antes da coleta real. `/admin/pesquisa`: escolher exercícios + iniciar, painel de participantes, sortear, encerrar, exportar CSV anonimizado (`utils/csvPesquisa.ts`: P01, P02…, sem UUID/nome).

## Modelo de dados
Banco principal: PostgreSQL via Supabase | Ferramenta de acesso: Prisma (`prisma-client`, `moduleFormat = cjs`, client gerado em `src/generated/prisma`)
Schema: `ide-web-backend/prisma/schema.prisma` (schema Postgres `public` do banco principal).

Banco do sandbox SQL (separado do principal, outro projeto Supabase): schemas `sandbox_<exercicio_id>_<usuario_id>`, um por aluno+exercício, fora do Prisma (DDL dinâmico via `pg`), criados sob demanda a partir de `Exercicio.sql_setup`; mais `sandbox_livre_<usuario_id>` do estudo livre, o único onde `sandbox_exec` recebe `CREATE` (sem `sql_setup`, não haveria tabela nenhuma pra consultar). Ver `docs/decisions/fase2-sandbox-sql-diagrama-mer.md`.

Entidades principais (banco principal): `Usuario` (papel: aluno/professor/pesquisador; `email`/`senha_hash` nullable no schema por herança, mas **obrigatórios para todos os papéis** via DTO desde a Fase 8), `MatriculaTurma` (aluno × turma, `@@unique([aluno_id, turma_id])` — o aluno pode estar em várias turmas ao mesmo tempo; guarda também `prova_id`, a variante sorteada **naquela** turma, que antes ficava em `Usuario`), `Turma` (+ `codigo`, `encerrada_em`, `turno`/`sala` opcionais só pro filtro do painel), `Prova` (`turma_id`, `titulo` — agrupa `Exercicio` pro sorteador de provas, ver Fase 5), `Exercicio` (nível: iniciante/intermediário; `modo_mer` — conceitual/logico/conceitual_logico, sempre definido pelo professor; `publico` — resolvível por qualquer aluno logado, sem matrícula, com correção só automática; `prova_id` opcional — null = visível pra turma inteira, senão só pro aluno sorteado com aquela prova, e **questão de prova não permite testar e aceita um envio só**; `prazo` opcional (null = sem prazo); combina até 3 partes por exercício — `mer_gabarito`, `sql_gabarito`, `gabarito_dissertativo`, cada uma opcional; + `sql_setup` — script de dados-exemplo do sandbox; + `gabarito_liberado`/`gabarito_liberado_em`), `DiagramaMer` (`@@unique([exercicio_id, usuario_id])`, autosave), `RespostaDissertativa` (mesmo padrão de `DiagramaMer` mas ainda sem `@@unique` nem endpoint de escrita — só leitura, usada no PDF), `SubmissaoSql` + `LogExecucaoSql` (explain), `SessaoAuth` (sessão de login com estado: 6h de teto, 1h de ociosidade, logout revoga — Fase 10), `ResultadoExercicio` (+ `finalizado_em`, quando o aluno encerra o exercício; + `envio_liberado_em`, o envio extra concedido pelo professor; correção: `sql_correto` agora é automática via sandbox SQL — compara conjunto de linhas do aluno com `sql_gabarito`, ignorando ordem —, `mer_avaliacao`/`dissertativa_avaliacao` seguem manuais; `@@unique([usuario_id, exercicio_id])`), `DicaIa` (contexto mer/sql, prompt/resposta/modelo/tokens).

`SessaoUso`, `RespostaSus`, `RespostaRtlx`, `TcleConsentimento` **não estão mais no Prisma/Supabase** — moraram aqui até a Fase 3, migraram pro backend Python self-hosted na Fase 4. `Usuario.grupo` (e o enum `Grupo`) também saíram na Fase 6 — o grupo agora é `AlocacaoGrupo` no Python, sorteado depois do TCLE (ver `docs/decisions/fase6-alinhamento-tcc.md`).

`SolicitacaoTurma` **saiu do schema** na Fase 4 (sem fila de aprovação: o código da turma já basta). `Usuario.turma_id`, `Usuario.prova_id` e `Usuario.codigo_pessoal_hash` **saíram na Fase 8**, junto das rotas `POST /turmas/:codigo/entrar|reentrar` — o vínculo virou `MatriculaTurma`.

### Setup manual pendente do módulo sandbox SQL
`SANDBOX_DATABASE_URL`/`SANDBOX_EXEC_DATABASE_URL` (ver `.env.example`) exigem, em produção, um segundo projeto Supabase com a role `sandbox_login` criada manualmente (`NOSUPERUSER NOCREATEDB NOCREATEROLE`, sem privilégio nenhum por padrão — é só a role de LOGIN da conexão de execução, que faz `SET ROLE` pra assumir a identidade `exec_<usuario_id>` de cada aluno; ver Fase 12, D13/D14). O grant por schema, e a criação de cada `exec_<usuario_id>`, acontecem em runtime pelo `SandboxProvisioningRepository` — a role apontada por `SANDBOX_DATABASE_URL` (provisionamento) precisa ter **`CREATEROLE`** em produção pra isso funcionar, além do que já tinha pra criar/derrubar schema. Local/dev usa o serviço `db_sandbox` do `docker-compose.yml`: `ide-web-backend/scripts/sandbox-init.sh` cria `sandbox_login` na primeira subida do container (volume vazio) — se o volume `db_sandbox_data` já existir de antes desta mudança (Fase 12), é preciso recriá-lo (`docker compose down -v db_sandbox` ou equivalente) pra rodar o script de novo, já que ele só executa contra um data directory novo.
